# Approved behavior handoff

Use only the sections needed for the task. Replace these instructions with project-specific facts before dispatch; an empty template is not approval.

## Outcome and authorization

State the user's approved outcome and any active discussion-only, hold or quota boundary. Approval of a scoped requirement allows work within that scope, not unrelated product changes.

## Existing behavior and data to preserve

Name the real interactions, capabilities and saved data that must survive. State which files or acceptance checks the worker may not change without owner approval.

## Observable acceptance

Write the simplest successful use, a repeated-use example, and the consequential failure or preservation case. Link the existing demo or parent-owned tests when available. Distinguish observed facts from assumptions.

## Implementation scope

List writable areas and actual integration points. Reuse existing working behavior. Do not invent mandatory confirmations, presets, allowlists or new data-clearing behavior. Report a product-level conflict rather than resolving it by changing the user's workflow.

## Verification and handoff

Run proportionate checks on the actual artifact. Report executed commands, useful results, changed files, an artifact path/revision and any concrete blocker. Keep detailed diagnostics in the checkpoint; the final summary need not repeat the implementation. Tests added by the worker supplement rather than replace owner-controlled acceptance.

## Deferred work

Name only genuinely deferred items; do not expand the backlog with speculative infrastructure.
